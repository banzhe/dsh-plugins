# @banzhe/dsh-devcontainer

## 0.2.0

### Minor Changes

- 5b843b1: Delegate every file operation of a `(devContainer)` session to the container instead of mapping container paths back onto the host bind mount. `DevcontainerFileSystem` now keeps a persistent `docker exec -i <container> node <helper>` process and speaks DSH's SSH helper framing to it (four-byte big-endian length header plus one UTF-8 JSON document, request/result/error/cancel frames, `SSH_PROTOCOL_VERSION = 3`), with a `hello` handshake that pins the protocol and the workspace. `resolve`, `lstat`, `stat`, `readText`, `streamText`, `readBytes`, `readByteRange`, `listDir`, `watch`, `writeText`, `editText`, `patchText`, `deleteFile`, and `moveFile` all become RPCs to a dependency-free Node program staged into `/tmp/.dsh-devcontainer/helper.mjs`, so paths, symbolic links, text decoding, atomic writes, and patches are computed inside the Linux namespace and the host filesystem is not reachable from a container-bound session at all. POSIX failures travel back as the DSH filesystem codes the seam already uses (`ENOENT` → `FS_NOT_FOUND`, `EACCES` → `FS_PERMISSION_DENIED`, `EISDIR` → `FS_NOT_REGULAR_FILE`, …). The row still fences containment — a request and every identity the container resolves must stay inside the repository's mount, or the call is refused with `FS_PERMISSION_DENIED` — and it still refuses a `(devContainer)` session over a repository that declares no container. An ordinary preset keeps the previous host backend and path mapping unchanged, a container-backed `watch` re-probes over RPC instead of opening a host watcher, and a container that restarts is recovered by staging the helper and handshaking again. Adds `rpcTimeoutMs` (default 60000) for one container filesystem request.
- 5b843b1: Add Docker Sandbox (`sbx`) support alongside the Dev Container driver. A `… (sbx)` preset derives from a new `sbxSources` list exactly like `… (devContainer)` derives from `sources`: same shell-tool flip, same depth-bounded subagent routing, but each track routes only into its own variants. A sandbox needs no `.devcontainer/devcontainer.json` — `sbx` mounts the host workspace at the same absolute path — so commands run as `sbx exec <name> -- /bin/sh -c "cd -- '<workdir>' && exec [env …] '<shell>' -c '<command>'"` from a deterministic `dsh-<repo>-<hash>` sandbox that is created (`sbx create --name … shell <root>`) and started detached (`sbx run --detach --name …`) on first use; a missing CLI is reported as an install problem rather than as a missing sandbox. `ctx.fs` delegates to the same container helper over `sbx exec -i <name> -- node …`, so every read and write happens inside the sandbox. New runtime markers `DSH_SBX` / `DSH_SBX_PRESET` join the Dev Container pair, `cli: "sbx"` is a valid driver (a declaration using it may also pin `workspaceFolder` and `sandbox`), and `presets.nameSuffix` is no longer configurable — `src/ids.ts` owns both suffixes and labels because the shell row reads a preset id back to decide which marker to set.
- 5b843b1: Add `@banzhe/dsh-devcontainer`: a Host Bundle that runs every agent command inside a repository's Linux Dev Container and makes the model believe it is already there. `ctx.shell` becomes a Docker-backed bash executor (explicit container, the running container the Dev Container CLI labelled, or `devcontainer up`) that reports Linux workdirs while spawning from the host repository root; `ctx.fs` maps `/workspaces/<repo>/…` back onto the Windows bind mount without touching the inherited write fence; the `working-directory:current` context states the Linux runtime and forbids PowerShell. A repository opts in with `.dsh/devcontainer.json`, `.dsh/docker.json`, `.devcontainer/devcontainer.json`, or `.devcontainer.json` (JSONC). On Windows it also adds a **Settings → Dev Container presets** page where each preset can be checked to derive a `… (devContainer)` variant that mounts `bash` instead of `pwsh` and routes its subagents to their own derived variants — route following is depth-bounded, and a route the cap stops is cut (an `allowedAgentPresets` entry dropped, a fixed `agentPreset` row disabled) instead of being left on the ordinary preset, which would start that subagent on the host; the choice is stored in the profile patch and applied live (register on check, dispose on uncheck) with no restart. Nothing is derived by default, presets that mount no shell tool keep mounting none, and no existing preset is modified. Container routing now follows the preset: a `… (devContainer)` preset runs every command in the repository's container, and an ordinary preset keeps the host shell it had — even in a repository that declares a container. Set `requireContainer: true` to make every session container-bound.

  A workdir outside every Dev Container repository keeps the platform's own local shell — bash on POSIX, PowerShell on Windows — so ordinary sessions behave as before. A `(devContainer)` preset over such a repository is guarded instead: the shell tools mark its calls through a `ctx.shellEnv` contributor, the working-directory context warns the model (and tells it to report to the user in Chinese), and the executor refuses the command with `exitCode: 1` rather than falling back to the host shell. This is the package's first release.
  Discovery no longer memorizes a missing declaration (`.dsh/docker.json` added after a failed lookup is picked up immediately) and re-reads a declaration whose `mtimeMs` changed; a container target that reports `No such container` / `is not running` is dropped so a restarted container is re-probed. The Host row builds its preset sync inside `ctx.inject(['loader', 'agentPresets'])` and re-derives on both `settings/document-updated` and `loader/volatile-update`, so a checked box registers its `(devContainer)` variant as soon as the tree is up — a lookup made at mount time would miss the Profile-patch registry row that activates later. Derived presets rewrite a persistent or terminal bash row into the plain `tool-bash` row — a PTY or persistent shell owns a HOST process, and on Windows the second terminal backend makes the whole variant mount as `broken` and disappear from every picker — disable every PowerShell row whether the dialect comes from the module or from `shellDialect: pwsh`, and rewrite `allowedAgentPresets`. The settings page retries its roster read after a write so a newly checked preset does not stay on "Wait for it", tags a variant that registered but cannot mount as unusable instead of calling it available, and an open preset picker re-reads its roster without a reload because a changed derived set is announced on `settings/document-updated` for the preset registry's namespace. The Docker / Dev Container CLI is started with a scrubbed environment rather than the inherited one: an allowlist of the names it needs to find `docker`, read the user's Docker configuration, write temp files, and honor locale and proxy settings, widened only by the `DOCKER_*` and `XDG_*` families and narrowed by the shared credential-name heuristic, so no harness credential or unrelated host variable reaches the CLI or the processes it starts. The container executor replaces the _sandboxed_ bash executor rather than the plain one, so `ctx.shell.sandboxMode` stays available: permission presets keep composing, host-side commands keep their confinement, and only a command that enters the container runs unconfined on the host. Rows activate correctly from a Profile that declares no `config:` for them, and a settings roster answer without a body renders an empty page instead of failing the plugin.

### Patch Changes

- fbfbd58: Report an absent path the same way inside a Linux container as on a Windows host: `resolve` now keeps the suffix under the nearest existing ancestor when a parent segment is a file, instead of refusing the whole path with `FS_NOT_FOUND`. A file used as a directory fails `realpath` with `ENOTDIR` on POSIX and `ENOENT` on Windows, and the helper treated only the second as absence, so `<repo>/a.ts/child.ts` resolved on a Windows host but was rejected inside the container; `stat`, `lstat`, `listDir`, and every read already reported that entry as absent, and `resolve` now agrees with them. Repository discovery also walks ancestors with the path module that owns the start path's spelling, so a Windows-shaped host path is no longer normalized by `win32` and then split by the platform module, which stopped the walk from finding the declaration above it.
- 5b843b1: Refuse host file access from a `(devContainer)` preset over a repository that declares no container. `ctx.fs` now reads the calling agent's preset — the initiating Agent's own Session answers `agentPresets.presetForSession`, so a subagent is attributed to its own preset — and, when that requirement holds and neither the path nor the base directory belongs to a repository that declares a container, refuses `resolve`, `lstat`, and every target-taking read or mutation with a structured `FS_PERMISSION_DENIED` whose diagnostic names the preset, the path, the four declaration files, and the two ways out. Nothing is read, written, or created on the host. A repository that declares a container is delegated to that container, an ordinary preset keeps the plain host filesystem, and `requireContainer: true` extends the refusal to every preset. The base-directory fallback that names a repository for a container path is conditional on ownership, so declaring a container in one repository no longer becomes a way to read an unrelated host directory (an absolute path elsewhere on the machine, or a relative path climbing out with `..`) from a `(devContainer)` session. Mutations a newer filesystem backend declares but this build does not type (`patchText`, `deleteFile`, `moveFile`) are wrapped when the inherited prototype provides them, so a caller holding a resolved target cannot skip the ingress check by calling one directly. The working-directory context now says file operations are blocked as well, not only shell commands. Both spellings a resolved target carries are fenced: the path the caller named and the realpath the backend performs I/O on. A symbolic link or junction inside the workspace that points at a host file outside it passes the first check and is refused by the second with the same `FS_PERMISSION_DENIED`, whose diagnostic names the named path, the resolved path, and the link; an ordinary preset keeps reading through the same link.
- 5b843b1: Run `run_code` programs in a directory the host can enter. Decorating `ctx.subprocess.spawn` did not reach the PTC worker: the runtime is asked for its own directory, so `resolve` filled a missing `cwd` from the sandbox policy's workspace root — the container's `/workspaces/<repo>` — and `run` handed it to the worker, whose entry program `process.chdir`ed into it. On a host that directory does not exist, so the program failed with `ENOENT: no such file or directory, chdir '/workspaces/<repo>'` before its first `tools.read`. `ctx.ptcRuntime` is now decorated at both entry points: `resolve` maps a directory the request names, and maps the directory the provider substitutes when the request names none, while `run` maps the spec's directory on entry so a caller holding a resolved spec cannot put a container path in front of the worker either. The translation is the same `toHostPath` arithmetic the spawn decoration uses — POSIX remainder plus the host root's own separator style, no drive letter constructed — so Windows, Linux, and macOS hosts share one code path. An ordinary session, a host path, a relative path, and a container path no declaration owns still reach the provider exactly as written, an unmapped request or spec is passed as the caller's own object, and unloading the Bundle gives the provider its own methods back.
- 5b843b1: Keep a `(sbx)` session's filesystem calls inside its sandbox mount. A Windows host's sandbox mounts the workspace at the drive-letter spelling of the host directory (`/f/personal/repo` for `F:\personal\repo`), while the specification a call was routed through still carried the drive path, so the workspace itself was refused as outside the repository. Routing now asks the runtime where the sandbox mounts the workspace before it attributes a path to a repository (the same probe the first call would run), every spelling of the mount counts as inside — the specification's folder, the drive-letter spelling, and the realpath the container reported — and an absolute path the mount does not hold is refused instead of being re-based onto it, so a sandbox session can no longer reach the container's own `/etc` through a path it named.
- 5b843b1: Resolve a `(sbx)` session's shell workdir to the host workspace it names. A sandbox spells a Windows drive directory without the drive colon (`F:\personal\asmr-manager` is `/f/personal/asmr-manager` inside it), and that spelling has no host ancestry for the repository walk to follow, so a command arriving with it resolved to no host directory and the `(sbx)` refusal fired. The shell row now reverses the spelling before asking the registry, and a row mounted without a `cwd` takes the workspace from the directory its workdir names, so `sbx exec` runs against the sandbox of that directory; a container declaration above it still wins.
- 5b843b1: Attribute a `(sbx)` session's filesystem calls to the workspace their path names. One row serves every session on the host, so its configured `cwd` is the directory DSH itself started in — under `dsh web`, the installed Bundle — while a `(sbx)` session names directories in its sandbox's spelling (`/f/personal/repo` for `F:\personal\repo`), which has no host ancestry for the repository walk to follow. The host directory is now recovered before routing gives up: from the mounts `sbx ls` reported, deepest first, which names the workspace root whether or not the repository declares a container, and from the drive convention only when a repository really declares a container above the directory it spells. A path outside every mount is still refused on the host, and `/f/…` cannot claim a host directory no repository declares.
- 5b843b1: Record the Session working directory as the host path of the repository, not the container's spelling of it. `DevcontainerFileSystem` inherited `processPath` from the host backend, so for a container-bound target it answered the container target key — `/f/personal/asmr-manager` for a `(sbx)` session over `F:\personal\asmr-manager`. `WorkingDirectoryService` commits exactly that value as the Session directory, so `workingDirectory.set` on a freshly started subagent replaced the inherited host directory with the sandbox spelling, and every host-bound consumer afterwards read it as a path in the wrong namespace: the project-root walk resolved `.git` against `F:\f\personal\asmr-manager\.git`, which is inside no repository and refused the turn, so a delegated `(sbx)` subagent failed before its first step. For a repository whose workspace is a Windows path, `processPath` now answers the host path of a container target; the container spelling keeps the two uses it owns, the argv a runtime is started with and the payload of an RPC request. A POSIX host is unchanged: its root already names the container namespace, so the recorded directory is the same path either way.
- 5b843b1: Start host processes in a directory the host can enter. In a `(devContainer)` session every seam speaks container paths — `ctx.shell` reports `/workspaces/<repo>/…` and the filesystem row reports the same spelling as the session working directory — so `run_code` handed the PTC runtime a directory that exists only on the container side, and the worker was spawned into it: `spawn … ENOENT` before its first `tools.read`. `ctx.subprocess.spawn` is decorated for that one decision: a working directory that belongs to a discovered repository is translated back onto that repository's host root with the POSIX remainder arithmetic and the host separator style the path module already owns, so Windows, Linux, and macOS hosts take one code path and no drive letter is constructed. An ordinary session, a host path, a relative path, and a container path no declaration owns reach the provider exactly as written, the caller's spec is otherwise untouched, and unloading the Bundle gives the provider its own method back. What the worker then does with files is unchanged: those calls are `ctx.fs`, which is the container RPC pipe.
