# Raising the Electron shell's window from a plugin

`app-notification` announces a finished Session and, on click, calls `window.focus()` before navigating. Measured on Electron 44 in the shell's own window states, that call does nothing: a backgrounded window stays unfocused, a window hidden by the shell's close path stays hidden, and a minimized window stays minimized. The shell hides the window instead of quitting it (`hideMainWindow`, `apps/desktop/src/main.ts`), so "hidden" is its ordinary resting state and not an edge case. The user clicks the notification, the Session switches behind whatever application is in front, and the window never appears.

**Why Chrome does what Electron does not.** Clicking a notification activates the window at the *browser* layer, not in page code. In Electron that request lands on `WebContents::ActivateContents`, which does nothing but notify observers (`observers_.Notify(&ExtendedWebContentsObserver::OnActivateContents)`); it never touches the native window. Electron declares no window-activation policy, while Chrome has one. So `window.focus()` is the wrong instrument — what raises a browser window is the browser.

**The renderer half is a dead end.** Probed on Electron 44: a backgrounded window stays unfocused, a window hidden by the shell's close path stays hidden, and a minimized window stays minimized — including after a real input click whose handler calls `focus()`. Two of those states are not focus questions at all: a renderer cannot make a window visible or un-minimize it, whatever permission it holds. Every other renderer spelling is closed too: `will-navigate` blocks the `dsh:` scheme without opening it, `setWindowOpenHandler` forwards only `http:`/`https:`, and the preload exposes a fixed `dshDesktop` surface with no window operation.

**The Node half is not.** This is the finding that reverses the earlier conclusion. The plugin's Node half runs inside the Host child — Electron Node mode (`ELECTRON_RUN_AS_NODE`), full Node APIs, `child_process` included, with `process.execPath` being the application binary. The shell claims a process-lifetime single-instance lock at module load and routes a later launch to `focusPrimaryWindow()` (`claimDesktopSingleInstance`, `apps/desktop/src/main.ts:1281`). So the Node half can raise the window by starting the application a second time, and that second instance quits on its own: `claimDesktopSingleInstance` returns false, `main()` never runs, exit code 0.

The click still happens in the client half, and the plugin already has a first-party way to reach its Node half: a Connection fetch route. `ui-deliverables` does exactly this today — its Node half registers routes with `ctx.connection.fetch.register({ path, methods, fetch })` (`packages/client/ui-deliverables/src/present-open.ts:20-54`), and any registered route reaches the Host. So the whole path stays inside the plugin: the client half's notification click `fetch`es a plugin-owned route, the Node half receives it, and the Node half spawns the application once. No harness change anywhere.

Measured, both synthetic and on the real packaged application:

| Measurement | Result |
|---|---|
| Electron 44 harness, window hidden, 8 runs | `secondInstanceFired=true`, `visibleAfter=true`, `focusedAfter=true` every time |
| Raise latency (spawn → `second-instance` handled) | 79 ms |
| Throwaway instance lifetime | 106 ms |
| Real packaged `DeepSeek Harness.exe`, window minimized | restored, `iconic=false`, **`foreground=true`**, 235 ms |
| Real packaged app, second launch while visible | exit code 0, 228 ms, no new window, process count unchanged |

So the plugin can deliver "click the notification, and the window comes back" with no harness change. The costs and risks to accept with it:

- It starts a whole Electron process to raise a window. ~80 ms to the raise, ~230 ms until that process is gone, per click. The `window.focus()` it replaces is free but does nothing.
- It works in production. In development the shell is launched as `electron <APP_ROOT>` with `--user-data-dir`, so a bare `spawn(process.execPath)` starts Electron's **default app**, not DSH — probed: it opens a stray window titled `Electron` and stays running. Development therefore needs the application path appended, or the same environment the launcher uses. Ship the production path; make development a no-op rather than a stray window.
- It raises whatever window the shell considers primary, and `focusPrimaryWindow()` also handles the destroyed-window case by recreating it. That is the desired behaviour, but it means the click can now start the application when it is not running — a real behaviour change, not just a raise.
- It depends on the shell keeping the single-instance handshake. That is load-bearing for profile ownership (two Desktops must never share `$DSH_HOME/profiles/desktop`), so it is unlikely to be removed, but the dependency should be recorded.
- The spawn must be non-blocking. `spawnSync` deadlocks the shell when the caller shares its main thread: the blocking call freezes the thread that has to process `second-instance`. Measured directly — a probe never raised anything until it switched to async `spawn`. The Node half is a different process, so the blocking form would technically be safe there, but the async form is what the measurement validated and what the plugin should use.
- The route is reachable by anything holding the connection's authentication, so it should be a POST with no body semantics and no side effects beyond the raise, and it should refuse when the shell is not the caller. It is the same fence the shipped routes already sit behind.

**Preferred shape, for comparison.** A validated one-way IPC on the existing `dshDesktop` preload API delegating to `focusPrimaryWindow` would do the same thing without starting a process: `send` rather than `invoke` so it cannot block the store write, issued after the click's navigation, guarded like every other product operation. It is the cleaner mechanism — one message instead of one process — and it needs a harness change. The spawn path needs none and is available today. Both end at the same function, so the spawn path is a shim that can be deleted once the IPC exists.

**Outcome: the IPC is implemented.** `dshDesktop.window.reveal` (`ipcMain.handle` + `ipcRenderer.invoke`, guarded by the existing `assertProductSender`) calls `focusPrimaryWindow` directly. `invoke` rather than `send` because `assertProductSender` already takes an `IpcMainInvokeEvent`, so the handler needs no signature change; the plugin treats it as fire-and-forget and swallows the rejection a refused guard produces. The spawn path was never implemented, so there is no shim to delete. Details and the two deviations from the original plan: [the proposal](../proposals/desktop-window-reveal-ipc.md).
**The stronger shape.** Let the Electron main process own completion notifications, beside the update notification it already owns (`update-attention.ts`, whose click handler brings its own UI forward). Completion is computed in the Host process, so the shell would need the fact forwarded over the existing `process.send` channel — `platform-session` and `update-tasks` are precedent, and `DESKTOP_HOST_PROTOCOL_VERSION` exists to version exactly this. It would also take over notification copy, the settings row, and the Web Profile's behaviour. Recorded rather than chosen: it is the most native design and the largest change, and the spawn path already delivers the user-visible outcome.

`window.focus()` is now the fallback rather than the instrument: the plugin calls `dshDesktop.window.reveal` where the shell offers it and only focuses in place where it does not (a browser, or a shell predating the channel). Scoping the call to the `web` Profile is therefore no longer needed — the capability probe already excludes the Electron path whenever the shell can raise the window itself.

## Correction log

An earlier revision of this document stated that no plugin-side mechanism exists and that raising the window required a harness change. That was wrong, and the error was mine, not the measurement's: the probes covered the renderer half and `require('electron')` in the Node half, and concluded from the second that the Node half was a dead end. `require('electron')` being unavailable does not imply `child_process` is — and `process.execPath` in the Host child is the application binary. The single-instance handshake was the missing piece, and it is documented in the shell's own source (`single-instance.ts`, whose event wiring exists precisely to raise the window on a second launch).

The claim "a renderer cannot raise the window" survived re-testing and is unchanged. The claim "the Node half cannot" was never tested and is false.
