# Stylesheets as files, loaded by the devkit

DSH serves a client bundle through `window.__ModuleLoader__.load({ id, factory })`: one named artifact, fetched with no bundler-owned page around it. A stylesheet is therefore never linked — it has to arrive inside `lib/client.js`. The Bundles that own CSS here kept it in a TypeScript template literal, which costs syntax highlighting, editor linting, and anything else that reads a stylesheet rather than a string.

Moving the text is not enough, because every obvious route is closed. tsdown 0.22 refuses a `.css` module outright (`tsdown:css-guard`), `loader: { '.css': 'text' }` does not get past that guard (the guard is a `transform` hook keyed on the id, not a loader lookup), and the official `@tsdown/css` either emits a sibling asset nothing requests or, in its inject mode, owns the `<style>` tag itself — these Bundles install that tag with a `data-plugin`/`data-plugin-css` owner and take it back with their fiber.

The loaders consequently live in `devkit/` (`@banzhe/dsh-devkit`, a private workspace package, TS source direct), and every browser build takes them from there: `x.module.css` compiles through lightningcss with CSS Modules (`[hash]_[local]`) and installs a tagged `<style>` while exporting the class map, a bare `x.css` installs one without a map, and `x.css?inline` hands the compiled sheet back as text for a plugin that owns the tag's lifetime. Virtual ids carry a null-byte prefix and an `.mjs` suffix so tsdown's guard never sees an id ending in `.css`, and each physical sheet is registered with `addWatchFile`. That is the semantics DSH's own `packages/client/tsdown.client.ts` gives its packages, restated for an out-of-tree Bundle because the preset is not importable — its loaders sit in a non-exported config factory and reach harness-internal paths; community plugin workspaces have arrived at the same shape independently. All three modes compile, so a bundle carries minified CSS and the pre-compile text lives only in the source file.

That last point decides what a Bundle's stylesheet specs can still assert. Vite resolves `?inline` for a spec and runs no lightningcss pass, so the text a spec reads is the source form while the shipped form is compiled: an assertion on a declaration's exact spacing then tests something no user receives. The repo's answer is to stop asserting sheet text in the Bundles and pin the loaders once, in `devkit/tests/`, over fixtures whose expected output is the compiled text. Each Bundle keeps what only it can prove: the tag id and its removal with the fiber, the `--dsw-*` names the sheet must use instead of literal colors, and the cascade the sheet produces (`getComputedStyle`, which no text assertion replaces). Formatting-tolerant checks are the exception, not the rule: two decisions jsdom cannot resolve — the reduced-motion block and the elevation-stroke rebind — stay pinned by pattern.

Each Bundle keeps its own tsconfig, tsdown config, and `src/client/css.d.ts`, sets `test.css: true` (Vitest stubs CSS to an empty module by default, which would let every stylesheet assertion pass vacuously), and declares the devkit in `devDependencies`. [0001](0001-monorepo-of-independent-bundles.md) prefers independent packages, so the cost is stated plainly: a Bundle copied out of this workspace no longer builds on its own. The devkit is worth that because the alternative was three copies of the same loaders, and because `devkit/tests/` is now the single place those loader semantics are pinned.
