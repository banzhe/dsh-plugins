# Browser halves built by one devkit recipe against the shell's module table

A Bundle here ships two halves: a Node half the Loader mounts and a browser half emitted as `lib/client.js` — a CommonJS factory registered through `window.__ModuleLoader__.load({ id, factory })`. That wrapper, the `lib` layout, the declaration-less browser build, the sourcemap, and the set of modules resolved from the page rather than bundled are the same for every Bundle; before this decision each of the ten client Bundles restated them in its own `tsdown.config.ts`, so a rule could drift in one package and only show up as a runtime failure: an inlined React renders outside the shell's tree, and a bundled store engine hands out a second copy of state the page already owns.

The rules now live in `devkit/src/tsdown-client.ts` as `clientBundle({ id, clientEntry?, node?, externals?, css? })`, returning the two tsdown configs in build order. A package states only what differs: its id (also the factory id), a client entry when its browser half is not `src/client/index.ts`, node-half overrides (extra entries, `clean`, `copy` for a program that ships uncompiled), and any module-table specifier it requests beyond the baseline. `cssPlugins` stays part of that recipe — a Bundle takes the stylesheet loaders by default rather than wiring them per package ([0009](0009-css-as-files.md)).

The baseline is the shell's frozen module table for DSH `0.2.2-rc.2`: React, Cordis, Zod, `@tanstack/react-virtual`, the client store, the slot registry, the UI primitives, and the dockkit. It is restated in the devkit as data instead of imported from the harness, for the same reason as the stylesheet loaders: the preset's helpers sit in a non-exported config factory and reach harness-internal paths, and this workspace must build from its own checkout. Consequences worth stating plainly:

- Matching is exact. A subpath of an external package is NOT swept into externals with it, because a package may publish a browser-safe `/shared` module (route names and wire payloads) that belongs inside the bundle; asking the page for a key its table lacks would fail at load time.
- A Bundle does not repeat baseline entries in `dsh.client.external`. It declares, in `dsh.client.inject`, the client packages whose services it actually injects — one edge per provider, each also declared in `peerDependencies` and `devDependencies`, so no inject edge names a package the manifest does not own.
- `dsh.client.inject` is derived from the services in a plugin's own `export const inject`, resolved to the package that provides each one in its client half; it is not derived from hook types that merely appear in a component's props.

The cost is the one [0001](0001-monorepo-of-independent-bundles.md) already accepts for the stylesheet loaders: a Bundle copied out of this workspace no longer builds on its own, and `devkit/tests/` is where the recipe is pinned. In exchange the wrapper, the external baseline, and the registration shape exist once, and a Bundle's build config says what it is instead of repeating how a client bundle is built.
