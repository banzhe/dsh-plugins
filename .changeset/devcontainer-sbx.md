Add Docker Sandbox (`sbx`) support alongside the Dev Container driver. A `… (sbx)` preset derives from a new `sbxSources` list exactly like `… (devContainer)` derives from `sources`: same shell-tool flip, same depth-bounded subagent routing, but each track routes only into its own variants. A sandbox needs no `.devcontainer/devcontainer.json` — `sbx` mounts the host workspace at the same absolute path — so commands run as `sbx exec <name> -- /bin/sh -c "cd -- '<workdir>' && exec [env …] '<shell>' -c '<command>'"` from a deterministic `dsh-<repo>-<hash>` sandbox that is created (`sbx create --name … shell <root>`) and started detached (`sbx run --detach --name …`) on first use; a missing CLI is reported as an install problem rather than as a missing sandbox. `ctx.fs` delegates to the same container helper over `sbx exec -i <name> -- node …`, so every read and write happens inside the sandbox. New runtime markers `DSH_SBX` / `DSH_SBX_PRESET` join the Dev Container pair, `cli: "sbx"` is a valid driver (a declaration using it may also pin `workspaceFolder` and `sandbox`), and `presets.nameSuffix` is no longer configurable — `src/ids.ts` owns both suffixes and labels because the shell row reads a preset id back to decide which marker to set.
