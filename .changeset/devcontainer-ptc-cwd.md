Run `run_code` programs in a directory the host can enter. Decorating `ctx.subprocess.spawn` did not reach the PTC worker: the runtime is asked for its own directory, so `resolve` filled a missing `cwd` from the sandbox policy's workspace root — the container's `/workspaces/<repo>` — and `run` handed it to the worker, whose entry program `process.chdir`ed into it. On a host that directory does not exist, so the program failed with `ENOENT: no such file or directory, chdir '/workspaces/<repo>'` before its first `tools.read`. `ctx.ptcRuntime` is now decorated at both entry points: `resolve` maps a directory the request names, and maps the directory the provider substitutes when the request names none, while `run` maps the spec's directory on entry so a caller holding a resolved spec cannot put a container path in front of the worker either. The translation is the same `toHostPath` arithmetic the spawn decoration uses — POSIX remainder plus the host root's own separator style, no drive letter constructed — so Windows, Linux, and macOS hosts share one code path. An ordinary session, a host path, a relative path, and a container path no declaration owns still reach the provider exactly as written, an unmapped request or spec is passed as the caller's own object, and unloading the Bundle gives the provider its own methods back.
