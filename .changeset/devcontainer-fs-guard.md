Refuse host file access from a `(devContainer)` preset over a repository that declares no container. `ctx.fs` now reads the calling agent's preset — the initiating Agent's own Session answers `agentPresets.presetForSession`, so a subagent is attributed to its own preset — and, when that requirement holds and neither the path nor the base directory belongs to a repository that declares a container, refuses `resolve`, `lstat`, and every target-taking read or mutation with a structured `FS_PERMISSION_DENIED` whose diagnostic names the preset, the path, the four declaration files, and the two ways out. Nothing is read, written, or created on the host. A repository that declares a container is delegated to that container, an ordinary preset keeps the plain host filesystem, and `requireContainer: true` extends the refusal to every preset. The base-directory fallback that names a repository for a container path is conditional on ownership, so declaring a container in one repository no longer becomes a way to read an unrelated host directory (an absolute path elsewhere on the machine, or a relative path climbing out with `..`) from a `(devContainer)` session. Mutations a newer filesystem backend declares but this build does not type (`patchText`, `deleteFile`, `moveFile`) are wrapped when the inherited prototype provides them, so a caller holding a resolved target cannot skip the ingress check by calling one directly. The working-directory context now says file operations are blocked as well, not only shell commands. Both spellings a resolved target carries are fenced: the path the caller named and the realpath the backend performs I/O on. A symbolic link or junction inside the workspace that points at a host file outside it passes the first check and is refused by the second with the same `FS_PERMISSION_DENIED`, whose diagnostic names the named path, the resolved path, and the link; an ordinary preset keeps reading through the same link.
